## Автоматизация ввода в Factorio — ПОСТОЯННОЕ РАЗРЕШЕНИЕ (05.09.2026)

Пользователь на своём основном ПК явно и заранее разрешил:

- **RCON — разрешённый канал автоматизации.** Подключение:
  `tooling/rcon_client.py` + `tooling/rcon_config.json` (host/port/пароль).
  Требует, чтобы игра была запущена через **"Host Saved Game"** (не обычный
  Continue) — тогда поднимается `local-rcon-socket` из
  `%APPDATA%\Factorio\config\config.ini`.
- **Полная автономия разрешена** — включая мутирующие команды
  (`build_blueprint`, `revive`, ремонт сущностей/проводов), не только
  чтение/диагностику. Не нужно спрашивать пользователя перед каждой
  командой или перед конкретной постройкой — действовать самостоятельно.
- Условие, поставленное пользователем при выдаче разрешения: прежде чем
  полагаться на мутирующие команды в новой сессии/после изменений в RCON-
  инфраструктуре — сначала убедиться, что read-only команды через RCON
  отрабатывают надёжно (без потери пакетов, без дублирования при повторной
  отправке). Это инженерная предосторожность, не запрос разрешения у
  пользователя — само разрешение уже дано и переспрашивать его не нужно.
- **Пока пользователь работает параллельно на этом ПК** — RCON никак не
  использует его мышь/клавиатуру/фокус окна, конфликтов с обычным
  использованием ПК нет. Единственное условие — не закрывать запущенную
  через Host Saved Game игру.

### Технические особенности RCON у Factorio (проверено вживую 05.09.2026)

Валидировано: 35/35 круговых запросов (25 подряд на одном соединении + 10
свежих переподключений) без единого сбоя — read-only-надёжность
подтверждена, условие пользователя для перехода к мутирующим командам
выполнено.

- **`game.player` через RCON всегда `nil`** — RCON выполняется в серверном
  контексте, не от лица конкретного игрока. Все Lua-шаблоны из
  `AUTOMATION.md`, написанные для ручной вставки (`game.player.surface`,
  `.force`, `.position`), при отправке через RCON нужно переписывать:
  `game.players[1]` вместо `game.player`, `game.surfaces["nauvis"]` вместо
  `game.player.surface`, `game.forces["player"]` вместо `game.player.force`.
- **RCON-протокол Factorio не конвейеризирует запросы** — второй пакет,
  отправленный до чтения ответа на первый, молча игнорируется без ошибки.
  Строго чередовать send → recv → send → recv в `tooling/rcon_client.py`
  (уже реализовано так).
- **RCON не отвечает на пустую команду** — нельзя слать пустую
  команду-маркер (обычный трюк Source RCON для многопакетных ответов) —
  подвешивает клиент навсегда. Не нужно и без него: Factorio всегда
  отвечает ровно одним пакетом на команду в этом проекте.
- **`game.print(...)` не долетает до RCON-ответа** (уходит в игровой чат,
  тело ответа пустое) — для текста в самом RCON-ответе использовать
  `rcon.print(...)`. Для передачи больших данных, как и раньше — писать в
  файл через `helpers.write_file(...)` и читать
  `%APPDATA%\Factorio\script-output\*.json`, RCON только запускает команду.

Диагностический скрипт при новых протокольных сюрпризах —
`tooling/rcon_debug.py` (печатает сырые пакеты запрос/ответ).

### Живой Lua API Factorio — накопленные гочки (проверено вживую)

- **`LuaWireConnector.disconnect_from(target)` без ВТОРОГО аргумента
  МОЛЧА НЕ РАБОТАЕТ** (06.09.2026) — возвращает `ok=true`, но провод не
  удаляется. Нужен явный origin, ТОТ ЖЕ, что при `connect_to`:
  `con.disconnect_from(target, defines.wire_origin.script)`. При
  подозрении на баг disconnect/connect API — сначала минимальный
  изолированный тест (2 entity, connect, проверить count, disconnect,
  проверить count), не гадать на сложной живой схеме — сэкономит часы.
- Ремонт проводов с допуском поиска шире ~1 тайла ОБЯЗАН сверять полную
  конфигурацию сущности (не только имя+позиция) — иначе можно найти
  СОСЕДНЮЮ сущность того же типа с другой ролью и создать неверную
  спайку (см. `factorio_known_gotchas` в памяти).

**Что остаётся под постоянным запретом, без исключений:** эмуляция
ввода в окно Factorio — `SendInput`, `SetForegroundWindow` + нажатия
клавиш, автоматизация мыши/клавиатуры по самому игровому UI. Разрешение
касается ТОЛЬКО RCON (отдельный TCP-канал). Причина запрета — см.
`AUTOMATION.md` (шапка документа): в прошлом `SendInput` давал
недетерминированную доставку команд, что привело к слепому повтору
мутирующей команды и задвоенной постройке. RCON устраняет именно эту
причину (синхронный протокол запрос-ответ), поэтому разрешён отдельно от
общего запрета на эмуляцию ввода.
