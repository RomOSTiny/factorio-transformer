# Автоматизация ввода команд и скриншотов — статус и как использовать

> **ОТМЕНЕНО 12.08.2026 — НЕ ИСПОЛЬЗОВАТЬ SendInput/автоввод, несмотря на
> "РЕШЕНО" ниже.** Весь этот документ описывает автоматизацию, которую
> пользователь явно запретил после того, как она на практике оказалась
> ненадёжной: первая отправка новой команды часто не доходила до игры без
> видимой причины, слепой повтор — в том числе для МУТИРУЮЩИХ команд вроде
> `build_blueprint` — привёл к постройке с необъяснённым смещением/задвоенным
> счётом сущностей (сессия 12.08.2026, не диагностировано до конца, мир
> просто брошен). Пользователь прямо сказал: **"все команды в игру я ввожу
> вручную а то у тебя все багается"**. Актуальное правило — в памяти
> `feedback_factorio_debug_command`: генерировать Lua-команду, показывать
> её в чате (и класть в буфер через `Set-Clipboard` по запросу), ждать, пока
> пользователь сам вставит и подтвердит, потом читать файл-результат.
> **Никогда не вызывать `SetForegroundWindow`/`SendInput`/эмулировать
> нажатия клавиш в окно Factorio.** Раздел ниже оставлен как есть для
> истории — не как текущая инструкция.

Цель (историческая, недействующая): Claude сам вставляет Lua-команды в
консоль игры и сам делает скриншоты для проверки результата, без участия
пользователя в каждом шаге. Считалось "полностью решено" 09.08.2026 — см.
раздел "РЕШЕНО" ниже для того самого (более не используемого) рецепта.

## Актуальная процедура (12.08.2026) — как правильно строить в мире

Каждый шаг — один Lua-`/c`-однострочник, показанный текстом в чате (и в
буфере обмена по запросу). Пользователь сам вставляет в игровую консоль
(`` ` `` или `~`) и подтверждает Enter. Claude ждёт подтверждения, потом
читает результат из `%APPDATA%\Factorio\script-output\*.json` — никогда не
угадывает результат и не повторяет команду по своей инициативе, если файл
не появился (спросить пользователя, не слать повторно вслепую — именно
слепой повтор мутирующей `build_blueprint`-команды дал задвоенную постройку
12.08.2026).

**0. Перед ЛЮБОЙ постройкой — уточнить, в каком мире работаем.** Если
неочевидно из контекста сессии (например, после перерыва или если прошлая
сессия могла переключать миры) — спросить пользователя прямо, не
предполагать.

**1. Recon (обязателен на новом месте, не только при повторной ошибке).**
```
/c local surf=game.player.surface; surf.request_to_generate_chunks({x=X,y=Y}, RADIUS); surf.force_generate_chunk_requests(); local counts={}; for _,e in pairs(surf.find_entities_filtered{area={{X-W,Y-H},{X+W,Y+H}}}) do counts[e.type]=(counts[e.type] or 0)+1 end; helpers.write_file("recon.json", helpers.table_to_json({counts=counts}), false)
```
Смотреть на `counts` — если есть `unit-spawner` (гнездо биттеров), место
непригодно, выбрать другое. Пустой `counts={}` — можно строить. Площадь
recon должна быть НЕ УЖЕ, чем ожидаемый bbox чертежа (с запасом), иначе
пропустишь гнездо на краю.

**2. Генерация blueprint (Python/draftsman, локально, до игры).** Убедиться
в 0 `OverlappingObjectsWarning`/`ConnectionDistanceWarning` перед тем, как
переходить к игре — предупреждения ловятся мгновенно локально, дешевле
чинить здесь, чем через ремонтный пайплайн после постройки.

**3. Build (import_stack + build_blueprint в одной команде).**
```
/c local inv=game.create_inventory(1); inv[1].set_stack{name="blueprint"}; local ok=inv[1].import_stack("<СТРОКА>"); local built=inv[1].build_blueprint{surface=game.player.surface, force=game.player.force, position={x=X,y=Y}}; local n = built and #built or -1; inv.destroy(); helpers.write_file("build.json", helpers.table_to_json({import_ok=ok, entities_built=n}), false)
```
`entities_built` ДОЛЖЕН точно совпасть с числом сущностей в чертеже — если
меньше или 0 без видимой причины (recon был чист, чанки сгенерированы) —
не гадать, переспросить/перепроверить руками, не слать команду повторно
на автомате.

**4. Revive (отдельная команда, с `pcall` на каждый призрак).**
```
/c local surf=game.player.surface; local revived,failed=0,0; for _,e in pairs(surf.find_entities_filtered{type="entity-ghost", area={{X-W,Y-H},{X+W,Y+H}}}) do local rok=pcall(function() e.revive() end); if rok then revived=revived+1 else failed=failed+1 end end; helpers.write_file("revive.json", helpers.table_to_json({revived=revived, failed=failed}), false)
```
Несколько сущностей из общего числа обычно не оживают (~0.1-1%) — это
нормально, чинится следующими шагами, не повод для тревоги.

**5. Измерить реальный офсет локальные→мировые координаты (только вживую,
не аналитически по bbox — Решение 26).** Найти уникальный узел с известной
локальной позицией (например, `t_ctr`, если он есть в схеме — комбинатор
`signal-T + 1 -> signal-T` с самопетлёй) и вычислить `OX=real_x-local_x,
OY=real_y-local_y`.

**6. Ремонт сущностей (идемпотентный — проверяет наличие перед созданием,
безопасно повторять).** Манифест из декодированного blueprint (позиция +
конфигурация каждого arithmetic-combinator), для каждого — проверить бокс
±0.4 тайла, создать если пусто, применить те же `operation`/`signals`.

**7. Ремонт проводов (идемпотентный — точная проверка КОНКРЕТНОГО ребра
через `wireConnector.connections`, не через счётчик портов — Решение 26).**
Манифест проводов из того же декодированного blueprint, для каждого ребра
— найти оба конца по позиции (допуск 0.6 тайла), проверить существует ли
именно это соединение, создать `connect_to` только если нет.

**8. При сомнении в точности ремонта — точная проверка позиция+конфигурация
для КАЖДОЙ ожидаемой сущности** (не только "есть что-то рядом", а "то ли
это, что нужно") — надёжнее, чем нечёткое пространственное сопоставление в
плотной геометрии (Решение 27, `octave_precise_check.py`).

**9. Если нужна проверка временных/вычислительных багов — зарегистрировать
персистентный `on_tick`-логгер СРАЗУ после ремонта, до того как утечёт
время** (счётчик тиков в схеме не сбрасывается между шагами пайплайна;
K должен быть подобран с запасом в минуты, не секунды, чтобы пережить
несколько раундов ручной вставки команд — Решение 26/27).

**Общие правила по пути:**
- Область любой команды очистки/переписи — шире максимального bbox,
  когда-либо строившегося на этом месте за сессию, не только текущей
  версии схемы (Решение 27).
- Сущности через `position=` (не `tile_position=`) — локальная X должна
  быть явно дробной, не целой (Решение 26/27).
- `ConstantCombinator` опрашивать через `circuit_red/green`, не
  `combinator_output_red/green` (Решение 27).
- `ElectricEnergyInterface` НЕ подключать через `add_power_connection` —
  только близостью к столбу (Решение 27).
- Терминальный узел без потребителя даёт `get_signals()`=пусто всегда —
  добавить временного потребителя перед диагностикой (Решение 5/26/27).

## Что ТОЧНО работает (проверено вживую)

**Переключение фокуса на окно Factorio, нацеленное строго по PID/handle:**

```powershell
Add-Type @"
using System;
using System.Runtime.InteropServices;
public class Win32 {
    [DllImport("user32.dll")]
    public static extern bool SetForegroundWindow(IntPtr hWnd);
    [DllImport("user32.dll")]
    public static extern bool ShowWindow(IntPtr hWnd, int nCmdShow);
}
"@
$factorio = Get-Process -Name "factorio"   # или конкретный Id, если процессов несколько
$hwnd = $factorio.MainWindowHandle
[Win32]::ShowWindow($hwnd, 9)  # 9 = SW_RESTORE, на случай если свёрнуто
[Win32]::SetForegroundWindow($hwnd)
```

Подтверждено через `GetForegroundWindow()` — реально переключается (проверено
дважды, оба раза `Match: True`).

**ВАЖНО — единственный найденный, но критичный нюанс:** переключение фокуса
и всё, что должно произойти, пока Factorio активна (отправка клавиш,
скриншот), **обязаны быть в ОДНОМ вызове PowerShell**, не в раздельных
tool calls. Проверено эмпирически: разделение на два отдельных вызова
(один — переключить фокус, другой — скриншот) давало скриншот **редактора
кода**, не игры — то есть фокус откатывался обратно между вызовами
(похоже, среда, в которой работает Claude Code, сама забирает фокус между
вызовами инструментов). Объединение в один вызов эту проблему устранило —
скриншот после этого показал реальную местность игры.

**Скриншот всего виртуального экрана (все мониторы):**

```powershell
Add-Type -AssemblyName System.Windows.Forms,System.Drawing
$allBounds = [System.Windows.Forms.SystemInformation]::VirtualScreen
$bmp = New-Object System.Drawing.Bitmap $allBounds.Width, $allBounds.Height
$graphics = [System.Drawing.Graphics]::FromImage($bmp)
$graphics.CopyFromScreen($allBounds.Location, [System.Drawing.Point]::Empty, $allBounds.Size)
$bmp.Save("путь\к\файлу.png", [System.Drawing.Imaging.ImageFormat]::Png)
$graphics.Dispose(); $bmp.Dispose()
```

Работает — Claude потом читает файл через инструмент Read (поддерживает
изображения). Не нужно просить пользователя нажимать Print Screen и
присылать скриншот.

## РЕШЕНО: рабочий способ — `SendInput` со скан-кодами (не `SendKeys`)

**`SendKeys` не работает с Factorio (см. ниже, для истории) — но
низкоуровневый `user32.dll SendInput` с флагом `KEYEVENTF_SCANCODE`
(эмуляция на уровне скан-кодов, ближе к настоящему железу, чем то, что
шлёт `SendKeys`) — РАБОТАЕТ. Подтверждено файлом: `/c helpers.write_file(...)`
дошла и реально выполнилась в игре.**

Рабочий C#-код (через `Add-Type` в PowerShell), проверенный вживую:

```powershell
Add-Type @"
using System;
using System.Runtime.InteropServices;

public class InputSim {
    [StructLayout(LayoutKind.Sequential)]
    public struct KEYBDINPUT {
        public ushort wVk; public ushort wScan; public uint dwFlags;
        public uint time; public IntPtr dwExtraInfo;
    }
    [StructLayout(LayoutKind.Sequential)]
    public struct INPUT {
        public uint type; public KEYBDINPUT ki; public uint padding1; public uint padding2;
    }
    public const uint INPUT_KEYBOARD = 1;
    public const uint KEYEVENTF_KEYUP = 0x0002;
    public const uint KEYEVENTF_SCANCODE = 0x0008;

    [DllImport("user32.dll", SetLastError = true)]
    public static extern uint SendInput(uint nInputs, INPUT[] pInputs, int cbSize);
    [DllImport("user32.dll")]
    public static extern uint MapVirtualKey(uint uCode, uint uMapType);
    [DllImport("user32.dll")]
    public static extern bool SetForegroundWindow(IntPtr hWnd);
    [DllImport("user32.dll")]
    public static extern bool ShowWindow(IntPtr hWnd, int nCmdShow);

    public static void KeyPress(ushort vk) {
        uint scan = MapVirtualKey(vk, 0);
        INPUT[] inputs = new INPUT[2];
        inputs[0].type = INPUT_KEYBOARD;
        inputs[0].ki = new KEYBDINPUT { wVk = 0, wScan = (ushort)scan, dwFlags = KEYEVENTF_SCANCODE, time = 0, dwExtraInfo = IntPtr.Zero };
        inputs[1].type = INPUT_KEYBOARD;
        inputs[1].ki = new KEYBDINPUT { wVk = 0, wScan = (ushort)scan, dwFlags = KEYEVENTF_SCANCODE | KEYEVENTF_KEYUP, time = 0, dwExtraInfo = IntPtr.Zero };
        SendInput(2, inputs, Marshal.SizeOf(typeof(INPUT)));
    }
    public static void KeyDown(ushort vk) {
        uint scan = MapVirtualKey(vk, 0);
        INPUT[] inputs = new INPUT[1];
        inputs[0].type = INPUT_KEYBOARD;
        inputs[0].ki = new KEYBDINPUT { wVk = 0, wScan = (ushort)scan, dwFlags = KEYEVENTF_SCANCODE, time = 0, dwExtraInfo = IntPtr.Zero };
        SendInput(1, inputs, Marshal.SizeOf(typeof(INPUT)));
    }
    public static void KeyUp(ushort vk) {
        uint scan = MapVirtualKey(vk, 0);
        INPUT[] inputs = new INPUT[1];
        inputs[0].type = INPUT_KEYBOARD;
        inputs[0].ki = new KEYBDINPUT { wVk = 0, wScan = (ushort)scan, dwFlags = KEYEVENTF_SCANCODE | KEYEVENTF_KEYUP, time = 0, dwExtraInfo = IntPtr.Zero };
        SendInput(1, inputs, Marshal.SizeOf(typeof(INPUT)));
    }
}
"@

$factorio = Get-Process -Id <PID процесса factorio.exe>   # найти через: Get-Process | Where-Object MainWindowTitle -ne ""
$hwnd = $factorio.MainWindowHandle
[InputSim]::ShowWindow($hwnd, 9)
[InputSim]::SetForegroundWindow($hwnd)
Start-Sleep -Milliseconds 500

Set-Clipboard -Value '/c <команда>'
Start-Sleep -Milliseconds 200

[InputSim]::KeyPress(0xC0)   # VK_OEM_3 - клавиша открытия консоли (позиция backtick/ё)
Start-Sleep -Milliseconds 400

[InputSim]::KeyDown(0x11)    # VK_CONTROL
Start-Sleep -Milliseconds 50
[InputSim]::KeyPress(0x56)   # 'V'
Start-Sleep -Milliseconds 50
[InputSim]::KeyUp(0x11)
Start-Sleep -Milliseconds 400

[InputSim]::KeyPress(0x0D)   # VK_RETURN
Start-Sleep -Milliseconds 800
```

**Важные детали, почему это сработало там, где `SendKeys` — нет:**
- `KEYEVENTF_SCANCODE` — эмуляция через скан-код (`MapVirtualKey` переводит
  виртуальный код в скан-код), а не через виртуальный код напрямую. Это
  ближе к тому, что реально шлёт клавиатура на аппаратном уровне — именно
  это, судя по всему, видит RawInput/DirectInput, тогда как более "высокоуровневые"
  события от `SendKeys` — не видит.
- Как и с фокусом окна — **всё в одном вызове PowerShell**, тот же принцип
  что и раньше: переключение окна, вставка в буфер и отправка клавиш должны
  происходить в одном непрерывном скрипте.
- Проверка успеха — **через файл** (`helpers.write_file` в самой отправляемой
  команде), не через скриншот. Скриншоты остаются рабочими для визуальной
  проверки, но файл — надёжнее и однозначнее.
- Виртуальные коды клавиш, которые понадобятся: `0xC0` (открыть консоль),
  `0x11`+`0x56` (Ctrl+V, вставить), `0x0D` (Enter, отправить). Полный список
  кодов — стандартная таблица Windows Virtual-Key Codes.

## Для истории — что НЕ РАБОТАЕТ (SendKeys)

**Доставка нажатий клавиш через `SendKeys` в окно Factorio — не работает.
Подтверждено надёжно (не скриншотом — файлом).**

Тест: сфокусировать окно (проверенный рабочий способ выше) → положить в
буфер `/c helpers.write_file("autoinput_test.txt", "IT WORKED "..game.tick, false)`
→ отправить клавишу открытия консоли → `^v` (Ctrl+V) → `{ENTER}` →
проверить, появился ли файл
`%APPDATA%\Factorio\script-output\autoinput_test.txt`. Файл **не появился
НИ РАЗУ за 4 попытки с разными вариантами клавиши открытия консоли**:
`{ENTER}`, `ё` (буквальный символ), `{~}` (экранированный tilde, т.к. в
.NET SendKeys голый `~` без скобок означает Enter, не символ), обычный
`` ` `` (ASCII backtick без Shift) — то есть
команда до игры ни разу не дошла и не выполнилась, независимо от того,
какую именно клавишу открытия консоли пробовали. Это надёжная проверка (не
зависит от скриншотов/зрения — если бы Lua реально выполнился, файл бы
физически появился), и то, что ВСЕ варианты клавиши дали одинаковый
отрицательный результат, говорит: **проблема не в конкретной клавише, а в
том, что SendKeys в принципе не доставляет события до этой игры**.

**Вероятная причина:** Factorio, как и многие игры, вероятно читает ввод
через DirectInput/RawInput API напрквую (для отзывчивости управления), а
не через стандартную очередь оконных сообщений Windows (`WM_KEYDOWN` и
т.п.), куда пишет `SendKeys`/`keybd_event`. Симулированный ввод через эти
API синтетические игры нередко просто игнорируют, даже когда окно
технически в фокусе (`SetForegroundWindow` подтверждённо срабатывает — это
НЕ проблема фокуса, а именно недоставка событий клавиатуры).

Скриншоты (сфокусировать + `CopyFromScreen`) частично работают — видна
местность игры, — но HUD/чат/консоль ни разу не показались ни на одном
скриншоте, и на некоторых появлялись странные чёрные области (вероятно,
отдельная проблема GDI-захвата DirectX-окон, не связанная с вводом).
Скриншоты **менее надёжны, чем проверка через записанный файл** — для
любой будущей проверки "сработало ли" полагаться на файл, не на скриншот.

## РЕШЕНО (10.08.2026): вставка blueprint в игру — тоже полностью автоматизирована, без ручного Import string

До сегодня единственным шагом, требовавшим пользователя, была вставка
blueprint-строки в библиотеку чертежей (Import string) — консольные
команды это не умеют напрямую, `/c ...` не принимает данные такого рода
через обычный API. Найден и подтверждён вживую рабочий обходной путь:

```lua
/c local inv=game.create_inventory(1); inv[1].set_stack{name="blueprint"}; local ok=inv[1].import_stack("<BLUEPRINT_STRING>"); local built=inv[1].build_blueprint{surface=game.player.surface, force=game.player.force, position={x=X,y=Y}}; local n = built and #built or -1; inv.destroy(); helpers.write_file("result.json", helpers.table_to_json({import_ok=ok, entities_built=n}), false)
```

`import_stack` возвращает 0 (успех), -1 (успех с ошибками) или 1
(провал). `build_blueprint` строит те же ghost-сущности, что и обычная
ручная вставка (дальше — обычный `revive()`, ничего не меняется).
Проверено сквозным тестом: собранный этой командой демо-контур (25
сущностей, `proc_demo_export.py`) ожил на 100% (25/25) и дал верный
`signal-A=19` — та же цепочка, что и при ручной вставке.

**Важный факт, который сначала пугал, но не подтвердился:** консоль
`/c` **не имеет практического ограничения по размеру команды** —
проверено вживую на 500 КБ и 1.5 МБ (полноразмерная строка chertежа),
оба раза команда дошла и выполнилась корректно, без урезания. Значит
даже сырую blueprint-строку без обёртки `import_stack` можно было бы
слать прямо в `/c`, если бы для этого был смысл — но `import_stack` всё
равно необходим, чтобы превратить строку в реальные сущности.

**Единственный найденный сбой — не в размере, а в фокусе окна.**
`SetForegroundWindow` может вернуть `false` (переключение не удалось),
если в этот момент активно другое окно (например, пользователь или кто-то
ещё за тем же компьютером печатает в браузере) — Windows защищает
активное окно от кражи фокуса фоновым процессом. **Всегда проверять
возвращаемое значение `SetForegroundWindow`, не считать успех
гарантированным** — если `false`, команда ушла не туда (в то окно, что
было активно), и нужно повторить, а не считать шаг выполненным. Рабочий
обход — короткое нажатие Alt (`AltTap()`) непосредственно перед
`SetForegroundWindow`, снимает защиту Windows от кражи фокуса в
большинстве случаев.

**Итог: ручное участие пользователя для постройки/проверки схем в игре
теперь не требуется вообще** (кроме случаев, когда пользователь сам
хочет присутствовать/наблюдать) — весь цикл экспорт → вставка →
оживление → дамп сигналов делается автономно.

## Итог — как работать в новой сессии

**Полный цикл автоматизирован и подтверждён вживую (09.08.2026):**
фокус на окно по PID → `Set-Clipboard` с нужной Lua-командой → `SendInput`
(консоль-клавиша → Ctrl+V → Enter) → команда реально выполняется в игре.
Больше не нужно просить пользователя вставлять команды руками — только
общий контроль с его стороны, как он и просил.

**Рекомендуемый рабочий процесс для каждой команды:**
1. Сгенерировать нужную Lua-команду как раньше (текстом, с `/c` в начале).
2. Один PowerShell-вызов: фокус на `factorio.exe` по PID → `Set-Clipboard`
   → `SendInput`-последовательность (консоль → Ctrl+V → Enter) — **всё в
   одном вызове**, не раздельно.
3. Если команда сама пишет результат в файл (`helpers.write_file`, как уже
   принято в проекте, Решение 5) — читать этот файл для проверки. Это
   надёжнее скриншота.
4. Скриншот — по необходимости, для визуальной проверки (например,
   расположение сущностей на карте) — тоже можно делать самостоятельно
   (см. выше), но помнить, что изредка попадаются пустые/чёрные области
   на скриншоте (проблема захвата, не связана с самой игрой) — если
   скриншот выглядит пустым/подозрительным, переснять ещё раз, прежде чем
   делать выводы.
5. PID процесса `factorio.exe` меняется при каждом перезапуске игры —
   находить заново через `Get-Process -Name factorio` в начале сессии
   (или `Get-Process | Where-Object MainWindowTitle -ne ""` если имя
   процесса неочевидно), не хардкодить старый PID.

## Найдено 10.08.2026 (продолжение Этапа 2): несколько новых проблем фокуса и один тупик

**Консоль остаётся открытой после Enter — обязательно закрывать явно.** Отправка `Enter` в игровой консоли ПОДТВЕРЖДАЕТ команду, но НЕ закрывает саму консоль (в отличие от предположения "команда прошла — можно забыть"). При многих командах подряд без явного закрытия консоль/чат разрастается и в какой-то момент занимает весь экран длинной историей — со стороны выглядит так, будто "окно игры пропало" (пользователь дважды спросил об этом за сессию). **Фикс — всегда добавлять `[Win32]::KeyPress(0x1B)` (Escape) в конец каждой последовательности отправки команды**, после Enter, в ТОМ ЖЕ вызове PowerShell.

**Приём "Alt tap перед SetForegroundWindow" (из более старого раздела этого файла) при многократном повторении за сессию похоже вызывал переключение виртуальных рабочих столов Windows** — пользователь сообщил "ты создал 2 разных рабочих стола". Не подтверждено на 100% как причина, но подозрительно совпадает по времени с частыми Alt-нажатиями в этой сессии. **Рекомендация: не использовать Alt-tap трюк по умолчанию** — обычный `SetForegroundWindow` без него сработал в большинстве вызовов этой же сессии; держать Alt-tap в резерве только если `SetForegroundWindow` вернул `false`.

**Синтетическое колесо мыши (`MOUSEEVENTF_WHEEL` через `SendInput`) НЕ доходит до игры** — проверено вживую (15-20 тиков колеса, с позиционированием курсора через `SetCursorPos` над окном и без) — масштаб камеры не менялся ни разу. Та же категория проблемы, что раньше была с `SendKeys` для клавиатуры (игра слушает более "аппаратный" уровень ввода) — вероятно, для колеса мыши тоже нужен более низкоуровневый обход (не найден и не проверен в эту сессию). Если понадобится менять зум программно — это отдельная нерешённая проблема, не полагаться на `SendInput` с `MOUSEEVENTF_WHEEL`.

**Фокус иногда утекает в СОВЕРШЕННО постороннее окно посреди последовательности** (не в Factorio и не в VS Code) — за эту сессию команда однажды попала в адресную строку окна Edge (создав новую пустую вкладку с мусорным URL, не потеряв ничего важного — это была свежая пустая вкладка), и окно поиска Windows один раз оказалось в фокусе после отправки. Причина не установлена окончательно (возможно, совпадение с системными уведомлениями или побочный эффект частых `Alt`/`Escape` нажатий). **Практическая защита, подтверждённая эмпирически в эту сессию: проверять `GetForegroundWindow() == hwnd` СРАЗУ после `SetForegroundWindow`, прямо перед вставкой в буфер и перед каждым последующим нажатием клавиши** — если проверка провалилась, не отправлять остаток последовательности (риск попадания текста не туда), а переделать переключение фокуса заново с нуля.

**Окно Factorio также может оказаться свёрнутым (`IsIconic=true`) без явной причины между вызовами** — не то же самое, что "потеря фокуса на другое окно". Проверять `IsIconic` явно (`[Win32]::IsIconic(hwnd)`), не полагаться только на `GetForegroundWindow()` — окно может технически "не быть в фокусе ни у кого", будучи просто свёрнутым, что даёт иную картину при диагностике.

**Нерешённый тупик, оставленный на будущее:** `build_blueprint{surface=surf, force=..., position={x=900,y=2000}}` дважды подряд вернул `entities_built=0`, несмотря на `surf.request_to_generate_chunks({900,2000}, N)` + `surf.force_generate_chunk_requests()` перед вызовом (пробовано с N=20 и N=40 чанков радиуса — оба раза 0). На более раннем прогоне этого же проекта (900,1400) с радиусом 20 чанков постройка прошла успешно (`entities_built=1485`) — то есть сам приём в принципе рабочий, что-то конкретно про (900,2000) или про ЭТУ конкретную (более широкую после фикса паддинга, ~2174 сущности) схему ломается. Не диагностировано до конца — начинать следующую сессию с этого (диагностическая команда с `is_chunk_generated`/`get_tile` подготовлена, но результат не получен).

**Найдено 11.08.2026: надёжный способ разведки/генерации территории — `game.forces.player.chart()`, не `request_to_generate_chunks`+`force_generate_chunk_requests`.** Пользователь указал использовать для разведки всегда:
```
/c game.forces.player.chart(game.player.surface, {{-1000,-1000},{3500,3500}})
```
`chart()` не просто помечает территорию видимой на карте — он гарантированно генерирует все чанки в area (в отличие от `request_to_generate_chunks`, который лишь СТАВИТ запрос в очередь, откуда и тянется нерешённый тупик выше про `entities_built=0`). Использовать этот приём как стандартную разведочную команду перед любой постройкой на новом месте — один вызов, большая область, не нужно подбирать радиус в чанках под конкретный чертёж.

**Осознанный риск, о котором стоит помнить:** без ручной проверки каждой
команды перед выполнением пропадает момент "посмотреть, прежде чем
нажать". За сессию закрытия Этапа 1 было около 6-7 случаев, когда первая
версия сгенерированной Lua была ошибочной (не тот API, не тот тип
сигнала) — раньше это ловилось, потому что пользователь читал ошибку и
присылал её. Теперь это всё ещё будет видно (через файл-результат/лог
игры), но уже ПОСЛЕ выполнения в реальном мире пользователя. Для операций,
которые безопасно повторить (создание сущностей, провода — уже в таком
стиле весь проект) — не страшно. Стоит быть особенно внимательным перед
любой потенциально необратимой командой (например, что-то удаляющее) —
лишний раз перепроверить логику до отправки, раз "второго шанса
посмотреть" от пользователя перед выполнением больше нет.
